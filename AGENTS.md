- Субагентов использовать по поручению пользователя или применимым инструкциям. Сначала выдавать каждому цель, источники, границы, формат результата и разрешённые файлы. Анализ и независимое ревью начинать без правок общих файлов; ведущий сопоставляет результаты и интегрирует их. При параллельной реализации разделять файлы/ветки/worktree; общие контракты и lockfile имеют одного ответственного. Не выдавать самопроверку за независимое ревью. На этапе подготовки субагенты возвращают предложения без правок общих файлов, ведущий интегрирует.
- Перед правками читать применимые инструкции и git status. Сохранять пользовательские изменения; не откатывать и не перезаписывать их. Не выполнять коммиты, push, деплой и внешние изменения без поручения. Не раскрывать секреты и данные пользователей.
- Перед задачей проверить текущую ветку и основную ветку репозитория (`main` или `master`, не предполагать имя). При чистом checkout переключиться на основную, выполнить `git pull --ff-only` и создать ветку задачи от обновлённой версии. При незакоммиченных изменениях сохранить их и предложить безопасный способ начала, не выполнять автоматический stash/reset/перенос. После реализации выполнить проверки карточки и просмотреть diff; в коммит включать только файлы задачи. При порученной публикации отправить ветку задачи в origin и сообщить имя ветки, SHA коммита и результаты проверок. Подробности — [Git-порядок](docs/agent-workflow.md#git-порядок).
- Существенные изменения архитектуры, зависимостей и продуктовых правил обсуждать до реализации. Не устанавливать инструменты и не менять системные настройки без отдельного поручения.
- Проверять типы, сборку и значимое поведение по мере появления инструментов; выбирать проверки по риску изменения. Не выдавать невыполненные проверки за успешные: явно указывать, что не запускалось и почему.
- Каркас: npm ci из корня, npm run dev:web / dev:api в двух терминалах, npm run typecheck / build для обоих workspace. Корневой npm test — Vitest для целостности build-комплекта, не тесты ещё не созданных бизнес-функций; E2E/lint scripts пока нет. [README](README.md), [каркас](docs/qa/e1-01-report.md), [build-комплекты](docs/operations/artifacts.md). Не выдавать отсутствующие проверки за выполненные; полный стек не устанавливать заранее.

## Работа с Git

- Владелец разрешил выполнять порученные этапы разработки, необходимые проверки, локальные зависимости проекта, commit и push ветки задачи без повторных подтверждений. Это не разрешение автоматически принять результат за владельца, merge в основную ветку или выпустить production; существенные новые продуктовые/архитектурные решения по-прежнему обсуждать. Ограничения среды/автоматической проверки разрешений сообщать конкретно, не выдавать их за отсутствие поручения пользователя.

- Перед задачей проверить status, текущую и основную ветку origin (main/master). При чистом checkout переключиться на основную, выполнить git pull --ff-only и создать ветку задачи. При незакоммиченных правках сохранить их и предложить безопасный способ начала, без автоматического stash/reset.
- После реализации выполнить проверки карточки и просмотреть diff, включая новые файлы. В коммит добавлять только файлы задачи; перед commit проверить staged diff и git diff --cached --check.
- Commit/push выполнять по поручению. Публиковать ветку задачи в origin; в отчёте указать имя ветки, SHA и результаты проверок. Push не означает принятие владельцем или слияние в основную ветку.

## Понятность и поддерживаемость кода

- Ясные предметные имена, небольшие функции/компоненты с одной ответственностью; HTTP, бизнес-правила и отображение разделены.
- Явные типы на границах, проверка недоверенного ввода, безопасная обработка ошибок. Не обходить типизацию через any или assertions без обоснования.
- Повторяющиеся правила выносить в общий модуль при реальном повторе; не создавать универсальные абстракции и дополнительные слои заранее. Комментарий объясняет причину/инвариант, а не пересказывает код.
- Избегать скрытых побочных эффектов, неявной связи и больших компонентов. Состояния/зависимости передавать явно, публичные API модулей держать небольшими.
- На ревью проверять читаемость, границы ответственности, обработку сбоев и значимое поведение тестами; следовать принятым соглашениям стека, а не добавлять инструмент ради формального «best practices».
