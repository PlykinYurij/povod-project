# Работа над «Поводом»

- «Повод» — сервис сайтов-приглашений и сбора ответов гостей. Карта и приоритеты документов: [docs/product/README.md](docs/product/README.md). Исходное ТЗ: [docs/povod-mvp-spec-v0.1.md](docs/povod-mvp-spec-v0.1.md); сохранять его содержание без изменений. Решения владельца: [docs/product/decisions.md](docs/product/decisions.md), приоритетнее исходного ТЗ. Вопросы: [docs/product/open-questions.md](docs/product/open-questions.md). Предварительный план: [docs/implementation-plan.md](docs/implementation-plan.md).
- Подтверждённая основа стека: Next.js / React / TypeScript, NestJS, PostgreSQL. Целевая архитектура по §9 ТЗ — монорепозиторий и модульный монолит. Выбор npm/pnpm и локального окружения пока не согласован; остальные библиотеки §9 — план, не уже установленные зависимости.
- MVP: бесплатный пилот, четыре шаблона, редактор-форма и предпросмотр, публикация по общей ссылке, RSVP без аккаунта гостя, кабинет RU/EN, приглашения RU, superadmin и обратная связь. До двух мест публикации (пауза не освобождает место) и 300 хранимых ответов на событие. Ответы сохраняются без автоматического удаления по сроку, экспорт — XLSX. Дата события не управляет сроком публикации. Платежи, игры, drag-and-drop, персональные ссылки и собственные домены клиентов вне MVP. Предлагаемые сроки и остальные лимиты §2 не считать утверждёнными.
- Порядок: подготовка → аналитика → архитектура и UX/UI → проверка согласованности → backlog → реализация небольшими этапами. Работать законченными задачами с явными границами, результатом и критериями проверки. Первая задача реализации — запускаемый каркас web/api, а не весь MVP.
- Субагентов использовать по поручению пользователя или применимым инструкциям. Сначала выдавать каждому цель, источники, границы, формат результата и разрешённые файлы. Анализ и независимое ревью начинать без правок общих файлов; ведущий сопоставляет результаты и интегрирует их. При параллельной реализации разделять файлы/ветки/worktree; общие контракты и lockfile имеют одного ответственного. Не выдавать самопроверку за независимое ревью. Текущий этап разрешает двух субагентов только для анализа.
- Перед правками читать применимые инструкции и git status. Сохранять пользовательские изменения; не откатывать и не перезаписывать их. Не выполнять коммиты, push, деплой и внешние изменения без поручения. Не раскрывать секреты и данные пользователей.
- Существенные изменения архитектуры, зависимостей и продуктовых правил обсуждать до реализации. Не устанавливать инструменты и не менять системные настройки без отдельного поручения.
- Проверять типы, сборку и значимое поведение по мере появления инструментов; выбирать проверки по риску изменения. Не выдавать невыполненные проверки за успешные: явно указывать, что не запускалось и почему.
- Сейчас package.json, lockfile, команд запуска, проверки типов, сборки и тестов нет. Не выдумывать команды. После создания инструментов записать реальные команды и результаты в документацию.
- При изменении поведения обновлять связанную документацию. Завершать задачу кратким отчётом: что изменено, что проверено, что осталось.
