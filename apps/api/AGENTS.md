# API: инструкции агенту

Действуют вместе с [корневым AGENTS](../../AGENTS.md). [Backend-conventions](../../docs/architecture/backend-conventions.md) — согласованные правила D-27; точные версии и параметры проверить до установки. [D-решения](../../docs/product/decisions.md) важнее старых вариантов ТЗ. Последние договорённости беседы также имеют приоритет, даже если ещё не вошли в main.

- Перед задачей: git status, [backlog](../../docs/product/backlog.md), конкретные FR/NFR, [API](../../docs/architecture/api-contract.md), [identity](../../docs/architecture/authentication.md), [QA](../../docs/qa/test-plan.md). Сохранять чужие изменения; не merge чужих веток, commit/push/deploy без поручения.
- npm workspaces, единый корневой package-lock.json, Node 26.13.0. Каркас E1-01 — Nest и root GET `/health`, без БД/auth/медиа/очереди. Из apps/api: npm run dev / typecheck / build / start; установка npm ci из корня. Dev — Node watch + ts-node, build — tsc, без Nest CLI. [README](../../README.md), [отчёт](../../docs/qa/e1-01-report.md). Стек целиком не ставить заранее, отсутствующие scripts не выдумывать.
- TypeScript strict, NestJS-модули по обязанностям: identity/projects/templates/publication/media/rsvp/admin/feedback. Controller — HTTP и DTO, service/use-case — правила/транзакция; доступ к БД внутри модуля. Не создавать все папки и универсальные base-классы без потребителя.
- Проверять вход в runtime, бизнес-правила в use-case, гонки в БД. DTO/interface/Swagger сами по себе не являются runtime-проверкой. Неизвестные/серверные поля запрещать; не передавать raw body в ORM. Optional и nullable различать; не делать неявное преобразование «false» в true.
- Guard/session недостаточно: каждый private ресурс проверять на ownerId. Чужой ресурс — нейтральный 404. Не принимать роль/ownerId/срок от клиента. CSRF, host-only cookie, no-store private responses, пароли только hash, токены/пароли/body анкет не логировать.
- Publication — одна транзакция адреса/снимка/формы/двух мест/90 дней/receipt. Повтор с тем же ключом не создаёт период. S3/SMTP/тяжёлая обработка вне транзакции. Server checks не заменять frontend-проверкой.
- Draft revision не затирается старым запросом. После публикации разрешены только текстовые коррекции по согласованному whitelist: новый immutable-снимок, прежние URL/period/formVersion. Не разрешать фото/структуру/дату/анкету под видом текста.
- Пауза занимает место; admin может остановить видимость без паузы расхода; владелец сам resume. Истечение 90 дней закрывает HTTP/RSVP/обычный экспорт и освобождает место без зависимости от cron, затем materialized soft-delete. Purge/restore Q-19 не выдумывать. Событие — только отображаемая дата.
- RSVP с первой публикации; до 300 хранимых записей атомарно, имя не уникально, отказ даёт ноль companions. Новый ответ при недоступности не принимать; повтор не воскрешает удалённую запись. Форма/TTL гарантий ещё открыты.
- Пользовательский slug выбирается при публикации, проверяется предварительно и окончательно уникальным constraint в транзакции; занятость — 409 без расхода места/периода. Не доверять произвольному Host/Forwarded-Host и routeUrl для server fetch. Изменение/повторная выдача адреса — по последним согласованным правилам, не предполагать.
- OpenAPI JSON с явными DTO, response/errors/operationId — источник Orval. Не отдавать ORM-объекты/passwordHash/private media keys. Generated client вручную не править; для его изменения нужен реальный контракт и координация с web.
- Согласованная validation-политика: ValidationPipe/class-validator, unknown fields — отказ, 422 с paths по API; malformed JSON — 400. Выбранные библиотеки — по D-27; параметры/TTL ещё Q-11. Не устанавливать без задачи.
- Миграции явные, SQL параметризован; тесты только на изолированной test-БД. Реальные constraints/гонки/транзакции проверять интеграционно, не моками. Typecheck/build/test после появления инструментов; не выдавать невыполненное за успех.
- Общий lockfile и контракты имеют ответственного; web/infra/worker scopes не менять молча. Итог: что изменено, реальные проверки/команды, не проверено и почему, открытые вопросы/риски. Существенные зависимости и архитектуру обсуждать до реализации.
