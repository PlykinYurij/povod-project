# Выполнение web-задачи «Повода»

Следуй [apps/web/AGENTS.md](../../../AGENTS.md) и корневым инструкциям. Этот skill задаёт процесс, а не дублирует правила frontend. Его наличие не разрешает установки, реализацию вне поручения, коммиты или внешние действия.

## Выбери область

Найди карточку и критерии в [backlog](../../../../../docs/product/backlog.md). При чисто документальной задаче не создавай приложение. При E1-01 следуй [первой карточке](../../../../../docs/product/first-task.md): не добавляй заранее весь согласованный frontend-стек.

Перед правками сравни ожидаемый результат с текущим git status и доступными файлами/scripts. Назови затрагиваемые routes/slices и владельца общих контрактов/lockfile. Создавай слой/adapter/provider только если есть потребитель.

## Прочти нужные источники

- Route/component/theme/i18n: [правила и обоснования](../../../../../docs/architecture/web-conventions.md), [UX](../../../../../docs/design/first-flow.md).
- Query/mutation/форма: [контракт API](../../../../../docs/architecture/api-contract.md), для auth — [identity](../../../../../docs/architecture/authentication.md). Проверь поля UI → DTO → field errors, client/server boundary и поведение повтора. Не подменяй отсутствующий endpoint ручным фальшивым успехом.
- Публикация/гостевая/slug: [адреса](../../../../../docs/architecture/publication-addresses.md), последние [решения](../../../../../docs/product/decisions.md). Проверь readonly-структуру, тексты, срок/паузу и неизменность адреса.
- Верификация: выбери применимые T/P/R из [QA](../../../../../docs/qa/test-plan.md); не переноси всё E2E в unit-тесты.

## Сделай проверяемый результат

Для UI выдели нормальное, пустое, ожидающее и ошибочное состояния. Для мутации различай отказ и потерю ответа после возможного commit. Для server rendering проверь, что публичный payload и client bundle не включают данные/провайдеры кабинета. Для генерации проверяй исходный OpenAPI и воспроизводимый generated diff, а не ручную правку результата.

Если вопрос блокирует часть задачи, свяжи его с конкретным Q/контрактом, продолжи независимую часть и не объявляй блокированную часть готовой. Существенное изменение требований или архитектуры вынеси владельцу до реализации; технические варианты не превращай в принятые правила.

## Проверь и передай

Запускай только существующие scripts в правильном workspace-контексте и проверки по риску изменения. UI — визуально mobile/theme/locale/keyboard по области; state/contract — подходящие Vitest/интеграционные проверки; RSC boundary — фактические typecheck/build после появления инструментов. Не устанавливай инструменты только ради красивого отчёта.

Заверши перечнем изменённых файлов, фактических проверок и невыполненных проверок с причиной. Обнови README/документацию при изменении команд/поведения. Самопроверку не называй независимым ревью.
