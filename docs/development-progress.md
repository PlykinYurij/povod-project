# Журнал разработки

Для каждой карточки сохраняй ссылку на проверенный коммит, результаты проверок исполнителя, вывод независимого ревью, результаты QA и ограничения. Для блокирующего дефекта укажи участок, решение и коммит повторного ревью. Если проверки выполнялись на разных коммитах, укажи SHA для каждой. Результат интеграционных проверок привязывай к SHA из `mvp` и записывай после их выполнения. Статус карточки веди в [backlog](product/backlog-v2.md).

Пробный проход по [backlog](product/backlog-v2.md) на базе [cc568c0](https://github.com/PlykinYurij/povod-project/commit/cc568c0295ddd5bfa9b41a4c2dc4a2df33ba8acf) остановлен на плане. Продуктовые задачи и ветки не запускались. В коде есть первичная публикация со сроком, маршрут снятия не найден. Ближайший этап — E4-01 и E4-01b, FR-12/20–22.

1. Ведущий сверяет D-43, A-03 и Q-29 и согласует контракт admin-only снятия и возобновления. Закрытие доступа гостям и RSVP, права редактора и сохранение существующего срока входят в разбор. Неясные детали расхода периода, нового заказа и цены блокируют только зависящие от них работы. [Вопросы](product/open-questions.md) · [Контракт](architecture/assisted-publication.md)
2. Дизайнер может параллельно уточнить состояния администратора, владельца и гостя в `docs/design`. Backend берёт согласованную часть E4-01 в `apps/api` и проверяет права, повторы, конкурентные операции и границы срока через `npm run test:database`.
3. Frontend готовит состояния E4-01b в `apps/web` по согласованным макетам и подключает реальный API после стабилизации OpenAPI. Проверки — `npm run test:web` и браузерные сценарии admin, владельца и гостя. Ревьюер и QA проверяют один и тот же SHA, DevOps подключается при блокере тестового окружения.
