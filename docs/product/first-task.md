# E1-01 · Минимальный запускаемый каркас монорепозитория

**Статус: Review.** Реализация и технические проверки выполнены, ожидается приёмка владельцем; это не Done/merge/production. E1-00 выполнен как необходимая подготовка в этом этапе, B-02 снят: [точные pins](../operations/toolchain.md). Доказательства — [отчёт T-01–06](../qa/e1-01-report.md), команды — [корневой README](../../README.md). Роль: ведущий разработчик; ревью — владелец/QA. Требования: NFR-13/14, структура §12 [ТЗ](../povod-mvp-spec-v0.1.md#12-репозиторий-роли-и-доска), поручение владельца о npm и root `/health`.

Границы и критерии карточки сохранены. Параллельно актуализирован существующий макет будущего первого сценария по отдельному поручению владельца; приложение не расширено до редактора/публикации.

## Проблема и результат

До выполнения в репозитории были только Markdown/HTML-макеты и README приложений. Результат этого этапа — два минимальных приложения в одном npm workspace, а не авторизация или весь MVP.

Результат одного PR: Next.js-страница «Повод» и NestJS GET `/health` с HTTP 200 и JSON `{"status":"ok"}` запускаются на Windows по проверенной инструкции. Health сообщает лишь о процессе, без БД/готовности бизнес-сервисов.

## Входит

- Корневые workspace manifest, поле `workspaces` корневого package.json, один `package-lock.json`, точный packageManager, Node engines/версия и необходимые конфигурации. Workspace apps/web и apps/api; packages создавать только при реальном потребителе.
- Минимальный Next.js App Router + React + TypeScript в apps/web, одна страница, локальные/системные шрифты без сетевого получения при build.
- Минимальный NestJS + TypeScript в apps/api, root GET `/health`, без глобального `/api/v1` prefix для этого endpoint. Бизнес-API позже остаётся `/api/v1`.
- Реальные scripts запуска каждого приложения, typecheck и production-build обоих; для одновременной работы достаточно двух терминалов, orchestration dependency не обязательна.
- Корневой README: версии, установка по lockfile, два запуска, порты, expected health, typecheck/build, остановка/restart, известные ограничения. AGENTS обновляется только реальными проверенными командами.
- Минимальные ignore/окончания строк и tool-конфиги по необходимости; не трогать исходное ТЗ и текущие docs/макеты.

## Не входит

Авторизация/reset, БД/ORM/миграции/seed, шаблоны приглашений/редактор, RSVP/XLSX, медиа/worker, Docker/WSL-переезд, CI workflow, серверы, деплой, Figma, GitHub-карточки. Не подключать Mantine/RHF/Zod/Query или генератор API без потребителя. Не писать тест, который только повторяет константу health; HTTP smoke достаточно для этого поведения.

Registry был доступен при установке/аудите. Карточка уже прошла реализацию и находится в Review; последующие операции требуют отдельной приёмки/поручения.

## Приёмка и способ проверки

1. **Workspace.** Два приложения используют один менеджер/корневой lockfile, точные tool pins; pnpm/yarn lockfile не появляется. T-01: npm ci установка в отдельной чистой копии не меняет lockfile. Новые данные не содержат секретов.
2. **Запуск.** T-02: из двух PowerShell-терминалов оба приложения стартуют по README без Docker/БД/production-секретов. Предложенные порты 3000/3001 документируются после фактической проверки. Конфликт порта не выдаётся за успешный старт.
3. **HTTP.** T-03: GET root `/health` даёт 200, JSON application/json и status=ok. Отдельно T-04: страница web открывается, заголовок «Повод», без ошибок приложения/консоли.
4. **Типы.** T-05: отдельные проверки типов web/API проходят с exit 0; наличие dev-сервера и build не подменяет typecheck.
5. **Сборки.** T-05: production-build web/API завершается 0, локальные артефакты созданы; нет скрытого сетевого шрифта. Это ещё не контейнерный релиз и не readiness БД.
6. **Воспроизводимость.** T-06: остановить и повторить запуски; проверить README в чистой копии, не удаляя пользовательские файлы. Сверить статус Git/изменения после проверки.
7. **Отчёт.** Записать версии, точные команды/exit codes, фактический ответ health, URL/порты и результат открытия страницы. Невыполненное указать явно, без статуса Passed.

Реальные scripts созданы и проверены: точный порядок установки, dev/typecheck/build/start — в корневом README. Отсутствующие test/lint scripts не выдавать за существующие или успешные.

## Разрешённые области и риски

Корневые manifest/lockfile/README/ignore/tool-конфиги, apps/web, apps/api; AGENTS и docs — для актуальных команд/отчёта. Никаких production-доступов. Сохранять существующие пользовательские изменения. Общий lockfile имеет одного ответственного. Избыточные зависимости или смена основного стека требуют обсуждения; выбранный в поручении npm повторно согласовывать не нужно.

## Не блокируют каркас

Q-04 форма, Q-16 whitelist текстов, Q-19 purge/restore/export, Q-09 media TTL, Q-10 правовая политика, Q-11 повторы/лимиты, Q-17 CSV. Docker/WSL и PostgreSQL нужны E1-05, не E1-01. Хосты/бюджет/ключи нужны деплою, не этой карточке.

После каркаса: **E1-02** — PR CI только для существующих проверок; **E1-05** — локальный PostgreSQL с изолированными dev/test без бизнес-миграций. Это отдельные PR и отдельное разрешение начать реализацию.
