Актуализация 19.11.2026: backend присутствует в main d19e115; web реализован и проверен на Review в feat/web-sign-in — [карточка](e1-04-identity-web.md), [QA](../qa/e1-04-identity-web-report.md). Ниже сохранены границы backend-карточки и её исторические доказательства.

Основание исправления регистрации: D-30, FR-02/03 и NFR-07/09 [исходного ТЗ](../povod-mvp-spec-v0.1.md), [решения D-28–32](decisions.md), [вопрос Q-21](open-questions.md#q-21--параметры-подтверждения-регистрации-fr-02-nfr-07).

## Проблема и результат

В main `6ccbf27` RegistrationService сразу создаёт User и Session. Требуется: email и пароль → письмо с кодом → подтверждение → завершённый аккаунт и автоматический вход. До подтверждения нет доступа к кабинету владельца, созданию черновика или публикации. Вход существующего аккаунта остаётся по email/паролю без кода. После входа не требуется повторное подтверждение для работы с проектом (D-02).

Зависимости: принятые E1-04/04b, принятые D-32 параметры (Q-21 закрыт); технический контракт фиксируется в начале задачи. E1-04c не обязательная зависимость: если тестовая почта уже сделана там, переиспользовать; иначе добавить минимальный локальный перехватчик в backend PR этой карточки. Общая почтовая доставка не должна образовать циклическую зависимость signup/reset. Production-провайдер выбирается отдельно, реальные письма/доступы не нужны для local-приёмки.

## Разделение на результаты по одному PR

1. **Backend + QA:** `apps/api/**`, необходимые локальные mail-настройки и backend-инструкции; контракт координирует ведущий. Pending-регистрация, выпуск/проверка/повтор кода, доставка в тестовую почту, миграция, обновлённый настоящий OpenAPI, интеграционные тесты. Общие зависимости/lockfile — один ответственный.
2. **Дизайн:** `docs/design/**`, после фиксации контракта — desktop/mobile экран кода и состояния. Вписать в существующий пакет identity, не создавать второй дизайн кабинета.
3. **Frontend:** `apps/web/**` и согласованный generated API client, после backend и ревью макетов — формы email/пароль и кода, resend, ошибки и переход после успеха. OpenAPI → Orval, без ручного дублирования типов. Использовать существующие frontend-правила и ролевой план; UI identity ещё не реализован.

Каждый результат отдельно проверяется и принимается владельцем. Backend можно принять без готового web, но весь сценарий не закрыт до сквозной проверки.

## Исходное предложение контракта (история); реализованный контракт ниже

- POST `/api/v1/auth/register` с email/password начинает pending, возвращает 202 с непривилегированным непрозрачным `registrationId`, `expiresAt`, `resendAvailableAt`; не возвращает user и не ставит auth-cookie. Это планируемое несовместимое изменение нынешнего 201, не работающий endpoint нового контракта.
- POST `/api/v1/auth/register/confirm`: registrationId/code → 201 с безопасным user и session-cookie после атомарного подтверждения. Ошибка кода нейтральная `REGISTRATION_CODE_INVALID`; лимит 429/Retry-After. Не возвращать код, пароль или hash.
- POST `/api/v1/auth/register/resend`: registrationId → 202, прежний код недействителен; после ошибки не показывать «письмо отправлено». Точное поведение ответа при неизвестной/просроченной заявке согласовать с Q-21; не раскрывать её содержимое.
- Сохраняются JSON/Origin/CSRF/no-store, 422 валидация, 409 EMAIL_UNAVAILABLE для подтверждённого аккаунта по D-28, 503 зависимости. UI различает принятую отправку и фактическую доставку, учитывает потерю ответа сети.

Pending хранит только hash пароля, не открытый пароль; код — защищённый проверочный отпечаток с назначением, expiry и счётчиком, не открытые шесть цифр/обычный перебираемый hash без серверного секрета. Код reset не подтверждает регистрацию и наоборот. SMTP вне DB-транзакции. Надёжность отправки/повтора после сбоя описать явно до реализации; не создавать самодельный универсальный брокер.

Подтверждение атомарно проверяет срок/попытки/одноразовость, создаёт User+Session и закрывает pending. SQL уникальность email остаётся последней защитой. Повтор после уже принятого confirm не создаёт ещё аккаунт или сессию: для первой версии предлагается нейтральная ошибка кода, UI предлагает обычный вход, если успешный ответ потерялся. Это техническое предложение для ревью контракта, не принятое новое продуктовое правило. Права не должны зависеть от запаздывания очистки pending.

## Критерии и доказательства

| Данные | Действие | Ожидается / проверка |
| --- | --- | --- |
| Новый синтетический email, валидный пароль | Начать регистрацию, запросить session и приватный ресурс до кода | Только pending, нет owner-session/прав/расхода квот; HTTP + PostgreSQL |
| Письмо в локальном перехватчике | Ввести код | Один аккаунт, hash пароля, сессия; автоматический вход; HTTP + manual UI |
| Неверный/истёкший/использованный код | Подтвердить | Нет автовхода и изменения чужих credentials; integration с управляемым временем |
| Pending одного email | Resend, затем старый код; смена email/новый старт | Старый код не подтверждает новые credentials; Q-21; integration |
| Один валидный код, два параллельных confirm | Подтвердить конкурентно и повторить | Не более одного аккаунта и успешной выдачи сессии; PostgreSQL constraint/transaction, не mock |
| Подтверждённый email, другой пароль | Начать/подтвердить повторно | 409 по D-28, аккаунт/пароль/существующие сессии не перезаписаны |
| Нет почты, ошибка БД, потеря HTTP-ответа | Старт/отправка/confirm/retry | Нет ложной авторизации/успеха; контролируемая ошибка/восстановление без дублей |
| CSRF/Origin отсутствует; лимиты достигнуты | Начать/подтвердить/resend | Отказ, 429 по согласованным параметрам; счётчики устойчивы к гонке |
| Код reset или другой pending | Подтвердить регистрацию | Отказ; purpose/email/pending связаны; нет утечки secret/code/hash в API/логах |
| Уже подтверждённый пользователь | Login, создать черновик по мере появления API | Вход без кода; нет дополнительного email-барьера |
| Desktop/mobile, клавиатура, RU/EN | Пройти email/пароль → код → успех | Loading, неверный/истёкший код, resend cooldown, смена email, почтовая ошибка и успешный переход; manual, затем подходящий E2E |

Обновить существующие HTTP-тесты, ожидающие немедленный 201/User/Session; не удалять проверки безопасности, duplicate/race и CSRF после выдачи Session. Перегенерировать snapshot из работающего backend, сверить Orval consumer. При реализации выполнить существующие `npm run typecheck`, `npm run build`, `npm test`, `npm run test:database` на отдельной test-БД; новые команды почты сначала реализовать/проверить и только затем документировать. Здесь проверки не выполнены, кода пока нет.

## Принятые параметры D-32

Код: 6 цифр / 10 минут / 5 неверных попыток; resend отменяет старый. Лимиты: 3 письма/email/час и 10 запросов/IP/15 минут, отдельно сохраняется register 5/IP/15 минут. Pending без прав и квот заменяется новым стартом на тот же email; старый код не подтверждает новый пароль. Подтверждённый аккаунт не заменяется. Удаление pending через 24 часа, expiry кода проверяется без cron. Технические поля/ошибки/повтор confirm выше остаются предложением контракта для ревью, но числовые правила больше не открыты.

## Реализованный backend-контракт

Start/resend возвращают только registrationId и expiresAt, без предложенного resendAvailableAt: отдельный cooldown не принят, rate limits сообщают Retry-After при 429.
