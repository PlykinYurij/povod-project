# MVP v2 · Приглашения с публикацией администратором

20.11.2026. Основание — новое поручение владельца, D-38/39. Это актуальная продуктовая рамка вместо самостоятельной бесплатной публикации. Исходное [ТЗ v0.1](../povod-mvp-spec-v0.1.md) не редактируется; FR/NFR сохраняют ID, изменения явно перечислены ниже. Существующий код не считается автоматически соответствующим новой модели.

## Подтверждено владельцем

- Зарегистрированный пользователь выбирает готовый шаблон, создаёт собственный проект-черновик, заполняет типизированную форму и заранее смотрит приглашение.
- Каждый шаблон имеет категорию события и фиксированную цену. Категории допускают свадьбу, день рождения, гендер-пати и дальнейшее расширение. Начальная поставка остаётся четырьмя шаблонами: два свадебных и два дня рождения/юбилея; список категорий не означает, что для каждой уже создан шаблон.
- Пользователь не публикует проект. Его действие открывает форму заявки: имя, телефон, выбранный канал связи Telegram / MAX / VK. В БД сохраняются контакты и ссылка на проект.
- Администратор работает с заявками, связывается с клиентом, согласует детали, затем сам запускает публикацию и задаёт доменное имя. Роль администратора — часть основного сценария MVP.
- Можно оставить заявку без готового проекта. Администратор по результатам общения создаёт проект из шаблона, заполняет его, публикует и передаёт ссылку клиенту. Обязательность аккаунта для такой заявки ещё не решена.
- Шаблоны могут иметь оригинальное оформление и сложные анимации. Строго типизированные формы обязательны; выбор JSONB или отдельных SQL-колонок не следует автоматически из этого требования и остаётся вопросом Q-23.
- Основной новый референс — [priglashyonline.ru](https://priglashyonline.ru/). Берём модель каталога/демо/заявки, собственные код/дизайн/материалы; [фактический разбор](../design/priglashay-reference.md).

## Что сохраняется из прежних решений

Next.js / React / TypeScript, NestJS / PostgreSQL / Prisma, npm workspaces, Windows/PowerShell, OpenAPI → Orval, React Hook Form, Vitest, правила web/API и CI/build-комплекты. Вход email/пароль, регистрация и reset через email-коды D-28–35 не меняются. Кабинет RU/EN, мобильный интерфейс, CSS Modules/themes, оригинальные приглашения отдельно от Mantine кабинета/admin.

Один проект использует одну фиксированную версию шаблона, смена шаблона не разрешена D-09. Форма с предпросмотром, фиксированный порядок и optional-блоки, все авторские тексты и выбранное фото редактируемы до публикации D-36. Лимиты полей D-37, пять черновиков, ограничения фото 10 / 15 МБ / 40 Мп и 300 хранимых RSVP сохраняются, пока владелец явно не изменит их. Admin-assisted проекты без User не должны обходить согласованные ограничения; точный учёт таких проектов — Q-25.

RSVP с первой реальной публикации D-16, общий адрес для гостей, отсутствие аккаунта гостя, работа с ответами/XLSX сохраняются. Форму контактов **заказчика** нельзя смешивать с RSVP **гостя**. Самостоятельные текстовые исправления после публикации D-17/36 пока не расширены до полной смены фото/структуры; новый порядок исправлений/снятия/повторной публикации требует Q-29.

## Что заменено или требует пересмотра

| Раньше | Теперь / статус |
| --- | --- |
| Бесплатный пилот и offer 0 ₽ | Фиксированная цена шаблона; конкретный прайс не утверждён. Сайт референса не задаёт наши цены |
| Владелец вызывает publish/resume и выбирает slug | Только администратор публикует и задаёт адрес; пользователь отправляет заявку. Прежнее право пользователя resume после admin-снятия больше не применять |
| Superadmin ближе к концу backlog | Admin permissions + очередь заявок + создание проекта по заявке нужны до первой продуктовой публикации |
| Два бесплатных места публикации | Бесплатная тарифная рамка заменена. Ранее принятый предел двух мест аккаунта пока сохраняется; его изменение и учёт admin-assisted — Q-26/25, не вводить безлимит молча |
| Бесплатные 90 дней / пауза расхода | Бесплатность заменена ценой шаблона. Ранее принятый срок 90 дней D-19 остаётся исходным до нового решения; Q-26 уточняет, хочет ли владелец изменить срок/паузу в коммерческой модели. Дата события срок не назначает |
| Feedback как второстепенная форма | Заявка — основной операционный объект. Feedback остаётся отдельным обращением, если понадобится |
| Первый сквозной сценарий заканчивается self-service publish | Шаблон → аккаунт → черновик → preview → заявка → admin review → admin publish → гостевая |

Платежи внутри приложения, эквайринг, автоматические сообщения в мессенджеры, произвольный no-code конструктор шаблонов, загрузка клиентского JS/HTML, drag-and-drop, собственные домены клиентов и персональные гостевые ссылки не добавлены новым поручением. Ручная коммуникация/согласование цены не означает реализованную платёжную интеграцию. Слово «открытка» пока относится к опубликованному приглашению, не к отдельному продукту поздравительных открыток.

## Предложения ведущего, не решения владельца

1. Не начинать новый репозиторий. Сохранить identity/CI/БД/рендерер/валидацию и расширить домен аддитивными миграциями.
2. В MVP администратор создаёт **проекты на основе готовых типизированных шаблонов**; новые сложные шаблоны добавляются разработчиком с кодом, схемой и renderer version. В админке — категория, цена, карточка, видимость и операторская работа. Нужен Q-30, если подразумевается создание совершенно нового дизайна без разработки.
3. Сохранять цену/версию цены и ревизию данных в заявке; публикация ссылается на явно проверенную версию, а не на случайно изменённый последним save черновик. Правила изменения цены/данных после отправки — Q-27/28.
4. Начать с поддоменов нашего сервиса по D-26, которые назначает admin. Под «доменом» не подразумевать автоматически покупку отдельного домена — Q-31.
5. Заявки без аккаунта хранить без фиктивных User/email. Проект с непривязанным заказчиком доступен только admin; привязка к клиентскому аккаунту должна подтверждаться отдельно — Q-24/25.

## Трассировка изменения объёма

FR-01/05–10/13–19/25 сохраняются с категориями/ценой/типизированным заполнением. FR-11/14 — публикация и передача ссылки через admin, не право клиента публиковать. FR-12/20–22 — пересмотреть точные права после публикации/сроки до реализации. FR-23 не заменяет заявки на заказ; добавлены требования R2-01–12 в [критериях](acceptance-criteria.md). FR-24 расширяется от модерации до ежедневной работы оператора. NFR-01–16 сохраняются; к изоляции владельцев добавляется изоляция admin/клиент/публичная заявка.
