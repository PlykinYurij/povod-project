# Публикация и пользовательский поддомен

Статус: единый web, SSR и правила адреса согласованы D-26. Конкретные DNS/TLS и политика повторного использования имён ещё проектируются. `povod.com` в примерах не означает, что домен приобретён или доступен.

## Одно web-приложение

Предложенная структура остаётся одной apps/web (Next.js): лендинг/каталог, кабинет, admin и гостевые страницы. Разные route groups/layout/providers/проверки прав, а не четыре независимые сборки. NestJS и worker — отдельные процессы. Backend проверяет owner/admin независимо от UI. Смена host не даёт права читать кабинет, session-cookie host-only.

Пример будущих origin: povod.com — лендинг, app.povod.com — кабинет, admin.povod.com либо защищённый /admin кабинета — admin, andrey-happy-birthday.povod.com — приглашение. Это один Next-артефакт, но маршрутизация по разрешённому host выбирает поверхность. Локально можно тестировать синтетические host-заголовки/localhost-адреса без покупки домена. Admin отдельным приложением можно выделить позже при обосновании; сейчас это усложнило бы выпуск.

## Что происходит при «Опубликовать»

1. Код шаблонов, Next.js, CSS и JS собираются при выпуске версии самого сервиса. Эта сборка общая, не на каждую свадьбу/день рождения.
2. Пользователь заполняет данные/анкету, выбирает адрес. Фото обрабатываются заранее, не во время publish.
3. NestJS проверяет сессию/поля/ревизию/готовность фото/два места и имя адреса. В одной транзакции резервирует slug, создаёт immutable-снимок контента и формы, выдаёт 90 дней, занимает место и пишет receipt операции.
4. После commit возвращает URL. DNS/сервер уже обслуживают wildcard-поддомены; не нужен новый сервер, контейнер, Git-репозиторий или CI-build на каждую публикацию.
5. Гость открывает host. Reverse proxy/Next проверяют допустимый базовый домен, извлекают slug и запрашивают NestJS. API разрешает выдачу только активной доступной публикации. Next SSR рендерит HTML из сохранённого снимка; общие CSS/JS и обработанные фото загружаются отдельно. RSVP отправляется в backend, это не «чистая статика».

**Согласовано для MVP:** SSR/no-store гостевого HTML, как ранее предложено. Зафиксированный контент не равен заранее собранному HTML-файлу. Это упрощает мгновенный запрет новых выдач после паузы/90 дней, исправления текстов и проверку прав. Цена — серверная работа при открытии. Кеш/CDN можно добавить после замеров с явной политикой отзыва.

Альтернатива: job генерирует HTML по каждому snapshot и кладёт в S3/CDN. Тогда появляются render-job/retry, атомарная смена версии, инвалидация, защита от устаревшей выдачи после истечения, отдельный статус «Публикуется». RSVP всё равно требует API. Не вводить эту инфраструктуру лишь потому, что пользователь нажал кнопку «Опубликовать»; если именно экспорт/хостинг статического HTML нужен продукту, надо отдельно выбрать этот вариант.

## Имя адреса и конкуренция

Принято: при публикации пользователь задаёт/меняет предложенную часть адреса, занятое имя не принимается. После первой публикации slug фиксируется (D-26), чтобы не ломать ссылки. Старый случайный publicId остаётся внутренним стабильным идентификатором, не заменяется строкой slug в связях БД.

Согласованные правила D-26: нормализованные lowercase ASCII латиница/цифры/дефис, 3–63 символа, без дефиса по краям/точек/пробелов; кириллицу можно транслитерировать в предложение, но не менять ввод молча. Зарезервировать app/admin/www/api/mail/support и другие системные имена; список в конфигурации. Slug не является доказательством личности или секретом. Конкретный полный список служебных имён хранится в конфигурации.

`GET /api/v1/publication-addresses/availability?slug=...` (owner-session, rate limit) → normalizedSlug/available/reason. Проверка во время ввода с debounce, ошибки «Имя занято»/«Недопустимое имя». Она предварительна и не резервирует имя. `POST /projects/{id}/publish` получает slug вместе с expectedRevision/offer version; финальная проверка и уникальный индекс нормализованного имени обязательны в транзакции. Если два publish гоняются, один проходит, второй 409 SLUG_TAKEN с path `slug`; второй не тратит период/слот и остаётся черновиком. Ключ повтора включает slug в хеш тела. Тот же ключ/тело возвращает прежний URL, другое имя требует нового ключа после подтверждённого отказа. Проверка сети не показывается как «имя свободно».

Предлагаемая сущность PublicationAddress: normalizedSlug unique, projectId, state reserved/active/tombstone, createdAt. До commit предварительных вечных резерваций нет. Политика tombstone/reuse после удаления — Q-20; переименование после публикации запрещено D-26. Не освобождать старое имя автоматически вместе со слотом: новый владелец старого адреса мог бы получить трафик из чужих QR/ссылок. Рекомендация — tombstone и отдельная политика повторного использования, срок ещё не выбран.

## Домен, доступность и тестирование

Wildcard DNS и TLS для выбранного базового домена настраиваются отдельно перед dev-проверкой. Exact системные hosts маршрутизируются раньше пользовательских. Wildcard не заменяет валидацию host: API/Next принимают только один разрешённый slug-label и настроенный base domain; не доверяют произвольному X-Forwarded-Host вне своего proxy. Служебные домены нельзя зарегистрировать пользователю. Host не превращается в путь файловой системы/S3 и не используется для построения reset-ссылок. Сертификаты/продление и фактический DNS проверяются отдельно, сейчас не создаются.

Кейсы: доступность→гонка двух владельцев→один успех; reserved/uppercase/invalid names; retry того же publish; смена введённого имени после отказа; неизвестный host без данных; пауза/истечение по тому же поддомену; доступность shared assets; отсутствие cookie кабинета на гостевом origin; TTL фото отдельно от HTML. Subdomain — адрес нашего сервиса, собственные домены клиентов всё ещё вне MVP.

Основание: D-19/20, FR-11/13/14. Проверено 11 ноября 2026: [NGINX server names](https://nginx.org/en/docs/http/server_names.html) описывает точные/wildcard hosts и их приоритет. Конкретные настройки DNS/TLS/провайдер и домен ещё не выбраны.
