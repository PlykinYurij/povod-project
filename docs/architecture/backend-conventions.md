Статус: стек и правила согласованы владельцем, D-27, 11 ноября 2026. Ничего не установлено; точные версии и параметры ещё проверяются. pg-boss остаётся кандидатом реализации согласованной PostgreSQL-очереди. ## Стек и границы

| Компонент | Рекомендация | Зачем / компромисс |
| --- | --- | --- |
| HTTP | NestJS со стандартным Express-адаптером | Меньше нестандартных интеграций в первом MVP; Fastify можно выбрать при измеренной необходимости, сейчас не нужны два адаптера |
| Данные | PostgreSQL + Prisma | Типизированные запросы и явные миграции, удобнее поддерживать одному frontend-разработчику. ORM не отменяет SQL/индексы/транзакции; сложный участок можно выразить параметризованным SQL после ревью |
| HTTP-валидация | Nest ValidationPipe + class-validator/class-transformer | Обычный для Nest путь DTO-классов, явно связывается со Swagger. Не вводить одновременно вторую схему HTTP-валидации на Zod без необходимости |
| OpenAPI | @nestjs/swagger, стабильные DTO и operationId | Орвалу нужен JSON-контракт с ошибками/response, не только красивый Swagger UI |
| Пароли/сессии | Argon2id + серверные сессии PostgreSQL | Пароль не расшифровывается, сессия отзывается на сервере. Не требуются долгоживущие JWT в localStorage |
| Медиа | S3-совместимое хранилище + Sharp в worker | БД хранит метаданные, а не фото; HTTP не занят тяжёлым декодированием |
| Jobs | Очередь на PostgreSQL, кандидат pg-boss | Уже есть PostgreSQL, можно избежать Redis. Выбор библиотеки/схемы очереди отдельный ADR перед jobs; не писать собственный брокер ради MVP |
| Проверки | Предлагается Vitest + HTTP integration (например Supertest), реальная test-БД | Общий runner с web удобен, но Nest decorators/metadata и трансформацию TS надо реально проверить; не обещать совместимость по названию runner |
| Стиль | ESLint + стандартный Prettier | Один подход с web; точные конфиги после каркаса |

Версии проверяются для Node 26.13.0 и npm workspaces до установки. В E1-01 лишь Nest и `/health`: Prisma, очередь, S3 и auth не должны попасть туда «заодно».

## Организация модулей

```text
apps/api/src/
  main.ts
  app.module.ts
  modules/
    identity/       # регистрация, сессии, reset
    projects/       # черновики, владение, ревизии
    templates/      # версии схем/форм
    publication/    # снимок, период, место, адрес
    media/          # приём файла, метаданные/доступ
    rsvp/           # приём и чтение ответов
    administration/
    feedback/
  common/           # только действительно общее: HTTP errors, requestId
  database/         # соединение/технические инструменты БД
```

Это ориентир, не список папок, которые надо создать сейчас. FSD предназначен для frontend; backend делится по продуктовым обязанностям. Controller принимает HTTP/DTO и вызывает use-case/service. Service проверяет права/правила и управляет транзакцией. Запросы БД остаются внутри модуля; узкий repository/query layer нужен при сложности, а не универсальный BaseRepository для каждой таблицы. Модули общаются через экспортированные сервисы, не через чужие private repositories. Общая инфраструктура не должна знать доменную логику.

Request → guards (сессия/CSRF/роль) → DTO validation → use-case (владение/срок/квота) → транзакция БД → явный response DTO. Guards не заменяют проверку конкретного ownerId в use-case. Значения ownerId/role/period/expiresAt берутся сервером, не из пользовательского body.

## Три уровня валидации

### 1. Форма запроса: можно ли его понять

Предлагаемая глобальная политика ValidationPipe: transform=true, whitelist=true, forbidNonWhitelisted=true, implicit conversion выключена. Строковые query/params преобразовывать явно и ограниченно; строка «false» не должна случайно стать true. TypeScript/interface не проверяет пришедший JSON во время выполнения.

- DTO — классы с явными правилами типов, границ длины/массива, enum и nested validation. Все внешние body/query/params проверяются. Optional (поле можно не прислать) и nullable (можно прислать null) описывать раздельно: `IsOptional` не использовать как случайное разрешение null.
- Ограничивать размер HTTP-body/загрузки до дорогостоящей обработки. Неизвестные поля отклоняются, а не передаются в Prisma через spread/Object.assign. Не принимать role/isAdmin/ownerId от регистрации или проекта.
- Неполный draft может сохранить незаполненные обязательные поля, но с правильными типами/максимумами. Publish требует полную версионированную схему. Для первого шаблона DTO/validator конкретные; произвольный JSONB не означает «принимаем любой JSON». Поля схемы документируются и валидируются одной серверной версией; клиент получает контракт через OpenAPI.
- Дата события проверяется как дата/время/пояс для отображения; никаких бизнес-ограничений по отношению к сегодня или сроку публикации.

### 2. Бизнес-правила: разрешено ли действие сейчас

Пользователь владеет проектом? Сохраняет актуальную revision? Ещё можно менять структуру? Фото готово и принадлежит проекту? Место публикации доступно? Анкета соответствует зафиксированной форме? Это проверки service/use-case, а не асинхронный `IsSlugFree`-декоратор.

Пример: валидный по форме slug может быть занят. GET доступности полезен UI, но окончательное решение — в publish-транзакции. Истечение 90 дней/видимость проверяются в обычном HTTP-чтении и RSVP, а не только cron. Просроченная запись не должна выдаваться, даже если deletedAt ещё не записан worker.

### 3. База данных: защита от гонок

Unique для нормализованного email и адреса публикации; FK/NOT NULL/нужные CHECK-ограничения; optimistic revision и атомарные операции квот. Два запроса «свободно?» перед двумя INSERT не являются защитой. Ошибка известного unique constraint переводится в соответствующий 409, остальные сбои не маскируются как «имя занято».

Publish атомарно фиксирует адрес/снимок/форму/место/90-дневное право/receipt. Один порядок блокировок (владелец, проект) во всех операциях квоты. Никаких S3/SMTP/декодирования файлов внутри этой транзакции. Повтор той же операции даёт прежний результат, а не новый период. Deadlock/serialization retry ограничен и не меняет idempotency key.

## Ошибки, ответы и документация

Невалидный JSON — 400; валидный JSON с неверными DTO-полями — 422 по существующему контракту (Nest default 400 надо явно настроить). 401 — нет сессии, 403 — CSRF/запрет роли, чужой/неизвестный private resource — нейтральный 404. 409 — конфликт ревизии/занятость/квота; 413 — слишком большой body/file, 415 — неподдерживаемый формат, 429 — частота, 503 — недоступность сервиса. Не возвращать 200 с error внутри.

Единая форма:

```json
{"error":{"code":"VALIDATION_FAILED","message":"Проверьте поля","fields":[{"path":"content.names.first","code":"REQUIRED"}],"requestId":"req-example"}}
```

Клиент локализует по code/path, message — безопасный fallback. Не включать в ошибку password/token/raw body/SQL/stack. Response маппится явно, ORM-объект не отдаётся целиком даже при совпадающих типах. Swagger описывает body, nested DTO, enum, nullable/optional, успешный response и все ожидаемые ошибки, cookie/CSRF и заголовок идемпотентности. DTO-декораторы Swagger не заменяют runtime-validation. Orval не должен угадывать `unknown` формы и не должен получать passwordHash в модели User.

## Авторизация, файлы и фоновые задачи

Следовать [identity-контракту](authentication.md): случайная session-cookie с отзывом/expiry, CSRF включая login, нейтральные login/reset ответы, одноразовый reset с отзывом старых сессий. Числа TTL/лимитов и алгоритм нормализации email ещё Q-11; подтвердить до реализации, не выбирать в скрытой константе. Rate limits не подменяют квоты 2/300 в транзакциях. Роль admin выдаётся отдельно, не через register payload.

Файл недоверенный: MIME клиента не доказательство, имя файла не S3-key/путь, ограничены байты/пиксели/время/параллелизм. ready только после успешной записи производных; защищать от повторов/сбоев/потери lease. Worker допускает повторную доставку, обработчики идемпотентны даже при заявлениях библиотеки об exactly-once. Надёжное создание job при доменном commit — в той же БД-транзакции либо через outbox; отдельно проверить совместимость очереди/ORM, не обещать атомарность «по умолчанию».

Soft-delete после истечения закрывает доступ сразу и освобождает слот, физическая очистка позднее по Q-19. Не удалять общий TemplateVersion или чужие файлы. Ретраи S3-cleanup безопасны, ошибки фиксируются без содержимого анкет. Логи структурированы, requestId, без body/cookie/reset URL/секретов; liveness `/health` не подменяет readiness зависимостей.

## Проверки до приёмки

Unit — расчёт остатка, whitelist текста, переходы состояний. HTTP+реальная test-БД — ValidationPipe/guards/constraints, два владельца, CSRF, гонки двух публикаций/ответов, retry после commit, миграции и effective expiry без cron. Моки Prisma не доказывают транзакцию. Swagger/schema и generated client сверяются с реальным HTTP, а не только друг с другом. Test-cleanup отказывается работать с dev/prod-role/connection string. Typecheck/build и команды — только после появления scripts.
