# Переход к MVP v2 без нового репозитория

20.11.2026. Рекомендация ведущего: **продолжать текущий проект**. Код приложения/SQL/данные в этой задаче не меняются. Основная переоценка — доменная модель и новые административные сценарии, а не смена технологий.

| Готовая часть | Действие |
| --- | --- |
| npm монорепозиторий, Next/Nest/TypeScript, CI, build kit | Сохранить; не создавать новый проект и не переустанавливать стек |
| PostgreSQL/Prisma/dev-test/миграции/изоляция | Сохранить; новые модели и backfill отдельными аддитивными миграциями |

## Последовательность миграционного проекта после ревью

1. Закрыть Q-23/24/25/26/27/28 в частях выбранного PR; выпустить ADR с выбранным хранением и владением admin-assisted проектом.
2. Добавить каталог категорий/шаблонов/версий и фиксированные цены. Привязать существующий wedding-garden-v1 к реальной TemplateVersion, сохранить его идентификатор и все тексты/ревизии существующих проектов.
3. При выборе SQL subtype: создать таблицы, перенести JSONB проверенным mapper, сверить количество/поля/Unicode/null/optional/порядок программы/14 copy, держать старые данные до проверки обратимости. Не удалять content в той же первой миграции. При JSONB такого переноса не требуется.
4. Добавить admin permissions, отдельные operator routes и аудит. Регистрация всегда создаёт обычного клиента; прежние аккаунты не становятся администраторами автоматически.
5. Добавить requests и закрепление согласованной версии/цены; затем клиентскую форму и admin list/detail/create-from-request. Обязательность User для общего обращения — Q-24.
6. Подключить медиа и первую анкету, затем admin-only атомарную публикацию/гостевой SSR. Реальных гостей не приглашать на промежуточный релиз без RSVP D-16.

Новые constraints/права/маршруты проверяются на test PostgreSQL и двух владельцах плюс admin. Старые проверки остаются регрессиями; их текущий успех не доказывает новую ролевую модель. Прежние raw SQL миграции и исходное ТЗ сохраняются без изменений. Production/backups/реальные аккаунты не трогать этим документированием.

Для отката сначала возвращается совместимый код; разрушительные удаления новых/старых колонок не предполагаются. Конкретный release migration/backfill rollback-план нужен в карточке изменения схемы. Решение создать новый репозиторий не даёт технической выгоды: самые дорогие для повторения инфраструктурные и identity-части уже подходят новой модели.
