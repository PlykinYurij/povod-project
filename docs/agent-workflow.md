# Параллельная разработка «Повода»

Работа идёт по [актуальному backlog](product/backlog-v2.md) и [решениям владельца](product/decisions.md). Действующий Git-процесс описан в [AGENTS.md](../AGENTS.md#работа-с-git). `mvp` служит базой задач и интеграции, `main` обновляет владелец вручную.

## Проектные роли

| Роль | Область | Результат и проверки |
| --- | --- | --- |
| [frontend](../.codex/agents/frontend.toml) | `apps/web` | Интерфейсы, локализация, адаптивность, доступность и интеграция OpenAPI. Проверки компонентов, сборка и сквозной сценарий по карточке |
| [backend](../.codex/agents/backend.toml) | `apps/api` | API, данные, миграции, изоляция, фоновые задачи. Typecheck, сборка, HTTP/PostgreSQL, проверки прав и повторов |
| [designer](../.codex/agents/designer.toml) | `docs/design` | Макеты, визуальные правила и состояния. Просмотр на заданных разрешениях, сверка API, клавиатура и длинные тексты |
| [code_reviewer](../.codex/agents/code_reviewer.toml) | Diff, вызывающий код, контракты и покрытие | Независимые замечания с SHA, строками, последствиями и воспроизведением. Блокирующие дефекты и улучшения перечисляются отдельно |
| [qa](../.codex/agents/qa.toml) | Рабочая версия задачи, назначенные тесты и `docs/qa` | Приёмка по критериям, автоматические и ручные проверки. Фактические результаты, шаги воспроизведения и доказательства дефектов |
| [devops](../.codex/agents/devops.toml) | `infra`, `.github/workflows`, `docs/operations` | Воспроизводимый запуск, CI/CD, dev/staging, мониторинг и восстановление. Проверки workflow и изолированной среды |

Ведущий выбирает карточки по проверенным зависимостям, договаривается о контрактах и назначает по одному владельцу на каждый общий файл. Общими считаются Prisma-схема и миграции, OpenAPI и его потребители, Orval-конфигурация, package-lock.json, корневые настройки, backlog и сводка. Backend предоставляет DTO, operationId, поля ошибок и правила доступа. Frontend использует версию контракта по согласованному SHA и генерирует клиент по правилам проекта. Ведущий объединяет части в ветке задачи и последовательно интегрирует готовые задачи в `mvp`.

Передай ревьюеру базовый и проверяемый SHA, карточку, ограничения и результаты проверок автора. Ревьюер возвращает замечания ведущему. Ведущий проверяет замечания, назначает исправления и возвращает новый SHA ревьюеру для повторной проверки затронутых участков. QA получает проверяемый SHA и критерии приёмки. Если QA находит дефект, исполнитель исправляет его, ревьюер проверяет изменённый код, QA повторяет затронутые сценарии.

При разработке тестов QA получает отдельный согласованный объём и worktree. Если две части меняют общий контракт или одним результатом образуют один API/UI-сценарий, ведущий согласует контракт заранее и планирует включение обеих частей в задачу. Рабочие копии агентов имеют разные ветки и индексы. Назначай отдельные порты и test-БД для параллельных проверок, если сценарии изменяют одно состояние.

## Git-порядок

1. Проверь `git status --short --branch`, локальные/удалённые ветки и `git worktree list`. Выполни `git fetch origin`. Для первой настройки действуют три варианта из [AGENTS.md](../AGENTS.md#работа-с-git). Если есть обе ветки `mvp` и `origin/mvp`, сначала пробуй обновить локальную через `git merge --ff-only origin/mvp`. Если история разошлась, проверь обе стороны и сохрани их. Известные локальные интеграционные коммиты можно объединить с `origin/mvp` обычным merge и повторно проверить. При неожиданном происхождении коммита сначала выясни его назначение.
2. Оставь корневой checkout на `mvp`. Для каждой задачи агента выдели свою ветку и worktree от актуальной `mvp`. Например, из корня после актуализации: `git worktree add -b task/e4-01-publication-lifecycle .worktrees/e4-01-publication-lifecycle mvp`. Каталог `.worktrees/` локальный. При пользовательских правках в корне отложи обновление и интеграцию до безопасного окна.
3. Выполни проверки карточки и ревью. В коммит добавь только файлы задачи, проверь результат `git diff --cached --check`. Повторно сделай fetch и обнови ветку задачи обычным merge актуальной `mvp`, если база изменилась. Разреши конфликты и повтори затронутые проверки. Сделай обычный push ветки задачи. GitHub PR используется, когда нужен hosted diff, проверка кандидата или этого требует защита ветки.
4. В корневом checkout актуализируй `mvp`, интегрируй одну готовую ветку, проверь объединённый результат и выполни `git push origin mvp`. Если удалённая ветка успела измениться, fetch и интеграция удалённой истории предшествуют повторным проверкам и push. При конфликте не выбрасывай чью-либо работу. Force-push, разрушительный reset и автоматический stash запрещены.
5. Зафиксируй проверенные коммиты, результаты ревью и проверок в [журнале разработки](development-progress.md). В ролевом плане выполнение, интеграция и явная приёмка владельцем отмечаются отдельно. Ссылки на старые фактические слияния в `main` сохраняются. Следующую доступную карточку в рамках порученного этапа можно брать после проверки её зависимостей в `mvp`. Production-релиз, платные ресурсы и изменения production-доступов требуют отдельного разрешения.

## Как вызвать роль

В доверенном проекте Codex CLI читает определения из `.codex/agents/*.toml`. У роли есть `name`, `description` и `developer_instructions`. Модель и разрешения оставлены на уровне текущей сессии. Для CLI укажи роль по имени и передай карточку. В среде, где именованные роли недоступны, ведущий читает TOML и задаёт те же границы встроенному субагенту. Если делегирование недоступно, ведущий выполняет доступные проверки, фиксирует отсутствие независимого ревью как блокер интеграции и продолжает независимые карточки. [Документация Codex](https://developers.openai.com/codex/subagents).

> Роль: [имя]. Карточка и результат: [ID, ссылка, объём]. База: [SHA mvp]. Ветка и worktree: [путь]. Зависимости: [SHA/API/дизайн]. Разрешённые файлы: [список]. Ответственный за общий контракт: [имя]. Проверки: [команды, данные и критерии]. Верни diff или SHA, результаты, ограничения и вопросы. Интеграцию выполняет ведущий.

## Инструменты и доступы

- Для CLI нужен доступный бинарник и авторизация для модельных запусков. В этой среде команда `codex` отсутствует в PATH. Установленный бинарник `codex-cli 0.169.0` запускается по полному пути из локального комплекта Codex. Для другой машины используй её установленный CLI. Проектные настройки проходят проверку доверия клиента Codex.
- В OPS-01 команда `codex debug prompt-input` через установленный бинарник подтвердила обнаружение пяти описаний ролей и загрузку корневых инструкций. Это локальная проверка конфигурации без модельного запроса.
- Для веток и worktree нужны Git, доступ на запись в checkout и метаданные Git, а для публикации — GitHub-аутентификация и разрешение на push в `mvp`. Если ветку защищают checks или PR, выполни установленный GitHub-процесс. Не обходи правила защиты.
- По задаче используй Node/npm, браузер для UI, Docker/PostgreSQL для локальных интеграций, права CI и изолированные dev/staging. Доступ к внешним макетам и ресурсам нужен только для соответствующего поручения. [Локальный запуск](../README.md) · [Операции](operations/README.md).
