# Разработка отдельными агентами

Это порядок выполнения [backlog](product/backlog.md), а не новый источник продуктовых правил. Планы: [web](../apps/web/development-plan.md), [API](../apps/api/development-plan.md), [дизайн](design/development-plan.md). Все новые пункты пока не выполнены.

## Перед параллельной работой

Во всём этом документе и ролевых планах `main` обозначает основную ветку: если в репозитории основной является `master`, использовать `master`.

1. Ведущий проверяет актуальный main и применимые инструкции. Backend-правила D-27 уже включены в `origin/main` на `387d161`: [apps/api/AGENTS](../apps/api/AGENTS.md), [backend-conventions](architecture/backend-conventions.md). Перед backend-задачей прочитать их, не переписывать договорённости заново.
2. Один ответственный выполняет E1-00, затем общий E1-01 по [карточке](product/first-task.md). Выбор точных совместимых версий ещё B-02. Нельзя одновременно создавать два разных workspace-каркаса из web и API.
3. Для каждого исполнителя — отдельная ветка и полный checkout через Git worktree либо отдельный clone. Рабочие папки `apps/web` и `apps/api` в одном checkout не изолируют ветки, index и переключения Git. Ветка задачи создаётся по Git-порядку ниже; создание дополнительных worktree/clone согласуется отдельно. В этом этапе они не созданы.
4. Рабочая папка frontend-агента — `<его-worktree>/apps/web`, backend — `<его-worktree>/apps/api` (не `app/api`), дизайнера — `<его-worktree>/docs/design`. Во всех случаях читать корневой AGENTS вместе с локальным.

Дизайнер может уточнять макеты до каркаса, если хватает продуктовых решений. После принятия каркаса web может готовить UI и рендерер по принятым макетам, API — БД и identity. Интеграция UI начинается после принятого контракта нужной функции; готовность одного направления не означает готовность другого.

## Git-порядок

1. До правок проверить `git status --short --branch`, текущую ветку и основную ветку репозитория. Имя основной определить по remote HEAD/данным origin, а не по имени текущей ветки. Если локальный `origin/HEAD` отсутствует, проверить HEAD удалённого origin; если это недоступно или неоднозначно, явно сообщить ограничение, не выбирать main/master произвольно.
2. При чистой рабочей папке переключиться на подтверждённую основную ветку, обновить её через `git pull --ff-only`, затем создать именованную ветку задачи от обновлённой версии. Если fast-forward невозможен, остановить подготовку ветки и объяснить расхождение; не заменять команду merge/rebase/reset без согласования.
3. При незакоммиченных изменениях сохранить всё на месте, перечислить затронутые файлы и предложить безопасный вариант. Например, отдельный worktree от обновлённой основной ветки либо сохранение текущей работы отдельным коммитом в своей ветке с разрешения владельца. Не применять stash, reset, clean и не включать чужую работу в задачу автоматически. До согласованного переноса не начинать новую реализацию в грязном checkout.
4. После реализации выполнить проверки назначенной карточки, просмотреть полный diff, включая новые файлы. Перед порученным коммитом добавить только явный список файлов задачи, просмотреть staged diff и выполнить `git diff --cached --check`. Если в одном файле смешаны чужие изменения, отделить свои фрагменты; не использовать массовое добавление без проверки состава.
5. Commit/push — по поручению. При публикации отправить именно ветку задачи в origin, без force-push и без прямого push в основную ветку. В отчёте указать имя ветки, SHA коммита, выполненные проверки/результаты и невыполненные проверки с причиной. Успешный push не означает принятие владельцем или merge.

## Значение чекбоксов

В каждой карточке ролевого плана три отдельных пункта:

- **Результат и проверки:** исполнитель ставит галочку только после выполнения своего объёма и отчёта с фактическими проверками. Если обязательная проверка не выполнена, галочку не ставить, указать причину.
- **Ревью владельца:** только после явного сообщения владельца о принятии конкретного результата. Молчание, push и открытый PR не являются принятием.
- **В main:** после сообщения владельца о слиянии и проверки наличия результата в актуальном main. Записать SHA интеграции, включая squash/rebase; SHA исходной ветки не обязан совпадать. При недоступном remote оставить этот пункт открытым.

Рядом с карточкой сохранять короткую запись: ветка/PR (если есть), SHA реализации, реальные команды и результаты либо ссылка на отчёт, подтверждение владельца, SHA main. Проверки могут быть ручными для дизайна. Макет с заглушками не доказывает интеграцию с API.

После одной карточки исполнитель **останавливается на ревью**. Следующую начинает по новой команде владельца и после принятия её зависимостей в main. Фраза «сделал ревью» без принятия или «готово» от другого агента не снимает зависимости. Можно обсудить независимую работу, но нельзя самостоятельно расширять поручение.

Общая карточка backlog завершена только после всех её ролевых частей и интеграционной приёмки. Локальная галочка web/API/дизайна не переводит её целиком в Done. Сводные статусы обновляет ведущий после сверки; исполнитель ведёт только назначенную ролевую карточку. Все зависимости backlog сохраняются, даже если в ролевом плане перечислены только основные.

## Владение файлами и контрактами

| Область | Ответственный |
| --- | --- |
| `apps/web/**`, web-план | Frontend |
| `apps/api/**`, API-план, исходный OpenAPI | Backend |
| `docs/design/**`, дизайн-план, автономный HTML | Дизайнер |
| Корневые manifests, package-lock.json, workspace-конфигурация | Один назначенный интегратор |
| `packages/api-client`, настройки Orval | Назначенный frontend-интегратор после принятого OpenAPI |
| Общие схемы шаблонов, API-документы, backlog, сводка | Один назначенный интегратор с согласованием потребителей |

Установка зависимости из workspace меняет общий lockfile: не начинать такие изменения одновременно. Исполнитель заранее сообщает нужную зависимость интегратору; разрешённые файлы и ответственный фиксируются в поручении. Не копировать lockfile из другой ветки целиком для разрешения конфликта.

Backend предоставляет DTO, operationId, поля ошибок, авторизацию, примеры и версию/commit OpenAPI. Frontend генерирует Orval из этой версии, не редактирует generated вручную. При несовпадении обсуждается контракт до реализации. Временные fixtures разрешены только в явно порученной UI-задаче, помечаются как имитация и не закрывают API/E2E-приёмку.

## Шаблон поручения

> Выполни только [ID и ролевую часть] по development-plan.md. База — принятый main [SHA]. Зависимости: […]. Разрешённые файлы: […]; общий lockfile/контракт ведёт […]. Критерии: […]. Сохрани пользовательские изменения. Отметь выполненный результат с доказательствами и остановись на моём ревью. Коммиты/push — только если явно поручены.

Команда продолжения, например: «Принял web-часть E2-02b, слил в main [SHA/PR]. Проверь результат и зависимости, затем выполни [следующая карточка]». Исполнитель сверяет факты, обновляет два приёмочных чекбокса и работает в своём checkout. При незакоммиченных изменениях не переключает ветку и не обновляет её с потерей данных.

Отчёт: что изменено; что проверено и чем; что не проверено и почему; вопросы/блокеры; какая карточка ожидает ревью. Команд приложения пока нет — их создаёт и проверяет E1-01. CI, среды и выпуск остаются отдельными задачами [операционного плана](operations/README.md); ни одна ролевая галочка сама по себе не разрешает production.
