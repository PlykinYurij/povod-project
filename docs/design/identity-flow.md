База main `0026548`, backend identity принят владельцем. [Открыть автономный HTML](identity-flow.html), [снимки](previews/identity-register-desktop.png), [проверки](identity-review.md). Это предложение UX для E1-04/04b/04c/04d и оболочки кабинета, не готовое приложение. Родительская E0-02 не закрывается одним пакетом. Источники: FR-02–05/25, NFR-01/06/07 [ТЗ](../povod-mvp-spec-v0.1.md), D-02/26/28–32 [решений](../product/decisions.md), [OpenAPI 0.4.0](../../apps/api/openapi.json).

Актуализация D-34: в действующем web добавлены обязательное имя, повтор нового пароля, шесть живых правил без пробелов, inline errors без native tooltip и компактные переключатели. HTML ниже — предыдущая итерация до D-34, не точный снимок актуальной формы; [фактические проверки](../qa/identity-review-report.md).

## Как смотреть

Открыть HTML в Chrome/Edge из WebStorm или файловой системы, сервер и установка не нужны. Верхняя панель принадлежит ревью, не продукту: экран, состояние, размер, тема, язык. Все данные синтетические; формы показывают переходы без API. Любые шесть цифр позволяют пройти демонстрацию — это не проверка подлинности кода.

Прямая ссылка поддерживает параметры, например `identity-flow.html?screen=code&state=expired&size=mobile&theme=dark&locale=ru`. Сами поля не сохраняются в URL/localStorage; URL задаёт только состояние макета. Язык инспектора RU/EN, продуктовые строки полностью переключаются. Гостевые приглашения по-прежнему RU, контент владельца не переводится.

## Пути и экраны

1. **Регистрация:** email/пароль → pending (202) → экран кода с адресом → confirm (201) → кабинет. До кода нет нового User/Session и доступа нового владельца. Автовход только после confirm; ordinary login без кода. Уже авторизованный браузер не превращается в новую учётную запись на start.
2. **Код регистрации:** одно поле шести цифр, а не шесть отдельных неудобных для вставки полей; inputmode numeric, autocomplete one-time-code, ведущие нули сохраняются. Resend не требует пароля. «Изменить email» возвращает на start; новый start создаёт новый ID и отменяет старую заявку/код. Пароль при возврате вводится заново, прототип его не сохраняет.
3. **Вход:** email/пароль → кабинет. Минимум поля пароля здесь 1, максимум 128: правила нового пароля не применяются к старому login. Неизвестный email/неверный пароль дают одно сообщение. Переходы к регистрации/reset; password reveal без отправки формы.
4. **Восстановление:** email → нейтральное подтверждение запроса → код и новый пароль → экран успеха → обычный вход. Ни начальный ответ, ни resend не раскрывают существование аккаунта. Успех сообщает об отзыве всех сессий, не изображает автоматический вход.
5. **Кабинет:** навигация и empty state первой регистрации, loading, ошибка, пример списка, пустой фильтр и expired session. При истёкшем входе карточек/квот владельца нет, только предложение войти. Пример списка не доказательство работающего project API. Переход «Выбрать шаблон» открывает существующий first-flow.html как соседний макет; создание/изменение проектов не имитируется как реализованное действие.

В реализации web (19.11.2026) выбраны `/register` и `/password-reset` с шагами в памяти одной страницы; отдельные confirm routes не нужны, API не меняется. Reload возвращает на старт с заранее показанной подсказкой. [Карточка реализации](../product/e1-04-identity-web.md). Остальные пути ниже — прежнее UX-предложение, а не обязательный routing-контракт.

Предлагавшиеся routes: `/register`, `/register/confirm`, `/login`, `/password-reset`, `/password-reset/confirm`, `/account`. Это UX-пути, не созданные Next.js routes и не новые API endpoint. Локализацию маршрутов/next-intl уточняет frontend в своей задаче.

## Поля → API → результат

Все мутации приложения получают свежий CSRF bootstrap/credentials по backend-инструкции. Сам макет запросов не делает.

| Экран | Поля запроса | Endpoint / ответ | Следующий шаг |
| --- | --- | --- | --- |
| Регистрация | userName: обязательное имя 1–80, trim, без управляющих символов; email: нормализованный email ≤254; password: 8–128, A–Z/цифра/спецсимвол, без пробелов/trim; повтор пароля проверяет форма, не DTO | POST `/api/v1/auth/register` → 202 registrationId/expiresAt, без User/session | Сохранить только ID/expiry в состоянии текущего flow, показать email-код |
| Код регистрации | registrationId из start; code: строка из 6 ASCII-цифр | POST `/register/confirm` под `/api/v1/auth` → 201 user + session-cookie | Обновить auth state; новый CSRF после смены Session; кабинет |
| Resend регистрации | только registrationId | POST `/api/v1/auth/register/resend` → 202 тот же ID, новый expiresAt | Очистить поле кода, показать сообщение/фокус code; пароль повторно не отправлять |
| Вход | email/password, пароль 1–128 без проверки нового состава | POST `/api/v1/auth/login` → 200 user + cookie | Обновить auth state/CSRF → кабинет |
| Запрос/reset resend | email | POST `/api/v1/auth/password-reset/request` → 202 message одинаковый для unknown/existing | Показать нейтральный экран кода, без утверждения существования аккаунта |
| Новый пароль | email, code, newPassword (UI password → DTO newPassword) | POST `/api/v1/auth/password-reset/confirm` → 204 | Очистить приватный query/auth cache, сообщить об отзыве всех Session → login |
| Текущий вход | без полей, cookie | GET `/api/v1/auth/session` → 200 user или 401 | Проверка приватной оболочки; 401 скрывает приватные данные |
| Выход | пустой JSON, Origin/CSRF | POST `/api/v1/auth/logout` → 204 | Очистить приватный cache и перейти к login |

Response expiresAt не передаётся обратно в confirm/resend: unknown fields → 422. registrationId и код reset не взаимозаменяются. UI не хранит session token в JS/localStorage; пользовательский код/password не попадают в URL, лог или analytics. В кодовом экране отсутствуют поля проекта — они относятся к следующей вертикали.

Для первой web-задачи предлагается хранить flow context в памяти: если после перезагрузки нет registrationId/email, вернуться к началу соответствующего сценария с пояснением, а не отправлять пустые поля в API. Сам код и пароль не восстанавливать из хранилищ. Долговременное продолжение flow и сохранение выбора шаблона после входа не утверждаются этим макетом; это независимые будущие уточнения.

## Состояния и ошибки

| Условие | Экран/поведение |
| --- | --- |
| Пустой ввод | Пустые формы register/login/reset; обязательные label, видимый focus, единые inline email/required checks; noValidate отключает браузерные всплывающие сообщения, ограничения отдельно на сервере |
| Запрос в работе | aria-busy, primary/input/resend disabled, сохранён контекст; скелетоны только для будущих данных кабинета |
| 422 VALIDATION_FAILED | По fields.path связать текст с нужным полем; userName/email/password/code/newPassword, не показывать raw server payload. В макете отдельный validation нового пароля, отдельно неверный код |
| 401 INVALID_CREDENTIALS | Одно сообщение для email/пароля, без указания, какой из них неверен |
| 400 REGISTRATION_CODE_INVALID / RESET_CODE_INVALID | Неверный/истёкший/исчерпанный/повторный код: нейтральная ошибка, resend или возврат к login; не раскрывать подробность по ответу сервера |
| Известное UI истечение | Макет expired. Реальное приложение использует expiresAt, но окончательное решение за сервером; не обещать клиенту оставшееся число попыток, которого API не возвращает |
| 409 EMAIL_UNAVAILABLE | Вход или восстановление; не заменять пароль подтверждённого аккаунта |
| 429 RATE_LIMITED | Disabled resend/primary и понятное ожидание из Retry-After. 15 минут в макете — пример, не всегда 15: email-окно может быть час |
| Сбой регистрации/почты 503 | Не показывать «аккаунт создан». Pending может остаться без активного кода; новый start допустим в лимите |
| Reset request 202 при недоставленном письме | Нейтральное подтверждение принятия, не гарантия доставки. Не менять на ошибку «нет аккаунта» |
| Потерян ответ confirm | Отдельное uncertain: код мог быть потреблён. Предложить обычный login с выбранным паролем; повтор не создаёт аккаунт/новый период. Для reset — login с новым паролем |
| 403 CSRF_FAILED | Технически получить новый bootstrap; повторять автоматически только заведомо отклонённый запрос, не потерянный confirm. После смены cookie всегда новый CSRF |
| Смена email/уход во время запроса | Инвалидировать локальный flow generation; поздний ответ старого запроса не возвращает экран/чужой registrationId. Отмена client request не доказывает отмену серверной мутации |
| 401 кабинета / logout | Скрыть private данные, очистить соответствующий Query cache, перейти к login; не смешивать owners A/B |

Ограничения D-32: до 5 start/IP/15 минут, до 3 писем/email/час и 10 запросов/IP/15 минут, код до 10 минут/5 неверных попыток, pending 24 часа. Resend не продлевает deleteAt. В UI нет выдуманного фиксированного resend cooldown или оставшихся попыток; API этого не отдаёт. Проверки срока публикации/архива не относятся к identity и не добавлены сюда.

## Стиль, адаптивность и доступность

Кабинет/формы ориентированы на согласованный Mantine через shared/ui; HTML — визуальное задание, не собственный UI-kit для копирования в приложение. CSS variables: surface/canvas/ink/muted/border/brand/error/focus, основной шаг 8 px, поля/кнопки минимум 46 px, radius 8–12 px (оболочка desktop 24 px). Светлая тема — тёплый нейтральный фон и зелёный; тёмная — отдельные семантические значения, не инверсия. System font без сетевых шрифтов. Оригинальный цветочный SVG — декоративный мотив, aria-hidden.

Desktop: двухколоночный вход с отдельной бренд-зоной; mobile 360 px: одна колонка, бренд-зона убирается, label/hint остаются. Длинные EN/RU и email переносятся. Ошибки имеют текст/role alert, успех/status; при переходе фокус на h1, после resend — code; Tab движется по native controls, видимый outline. Password reveal — type=button с доступным именем. В frontend обязателен field-level aria-describedby для текста ошибок по paths; не копировать глобальную ошибку как единственный способ идентификации поля.

## Границы следующей frontend-задачи

После owner review этого пакета: первая web identity-часть может реализовать login/logout/session и приватную оболочку с реальным API; затем signup/code и reset по тем же компонентам. OpenAPI → Orval, Mantine/shared/ui, next-intl, TanStack Query, CSS Modules/tokens согласно существующим правилам. Полноценный список/создание проектов не входит в первый identity PR: API отсутствует, mock-карточки не должны попасть в product как реальная функциональность.

Не выбраны автоматически: legacy-аккаунты Q-22, production mail, юридические тексты/согласия Q-10, состав реального project list/API. Эти вопросы не подменены checkbox или фиктивными endpoints в дизайне. Figma не использована: точный файл и доступ к записи не предоставлены, перенос отдельной задачей.
