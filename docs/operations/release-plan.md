# План dev → production

Основание: [ТЗ §10–11 и §14](../povod-mvp-spec-v0.1.md#11-devstaging-и-production), NFR-11–16. [CI E1-02](ci.md) уже реализован и проверен; выпускные workflow/серверы остаются будущей реализацией. Имена хостов, провайдеры, ключи, доступы и бюджет понадобятся в задачах деплоя; каркас ими не блокируется.

## Три порога готовности

| Порог | Что должно существовать | Доказательство |
| --- | --- | --- |
| E1-01 каркас | npm workspace, одна web-страница, API `/health`, scripts typecheck/build, README | T-01–06 из [QA](../qa/test-plan.md); без сервера/БД/CI |
| Первый dev-релиз | PR-проверки, неизменяемый комплект артефактов, закрытый стенд, отдельные env/ресурсы, synthetic seed и почта при их появлении | SHA/digest manifest, negative access-проверки, smoke/readiness и пробный откат демо-версии |
| Публичный пилот | Первая продуктовая вертикаль с RSVP, остальные обязательные FR/NFR MVP либо принятые исключения, мониторинг/backup/правовая готовность | Отчёты QA, восстановление БД/медиа, RPO/RTO, принятый владельцем точный SHA на dev |

Стенд может сначала принять минимальный демонстрационный сервис без данных. Он не обязан выдумывать миграцию/worker, которых нет; при появлении БД/медиа соответствующие проверки обязательны до выпуска их потребителя.

## Выпуск кандидата

1. PR: установка по lockfile, typecheck и сборки web/API; lint только после реальной настройки; значимые unit/API integration/E2E добавляются по поведению. Тесты используют test-БД, не обычную dev/prod. Ошибочный PR не должен проходить. В CI нет пользовательских анкет или prod-секретов.
2. После принятия main для точного commit SHA один раз собирается комплект web/API, worker и миграционного артефакта **когда они существуют**. Manifest связывает SHA, digests, версии, checks. «Один артефакт» означает один неизменяемый комплект, а не требование единственного контейнера.
3. Dev получает именно этот комплект, конфигурацию при запуске и отдельные ресурсы. Не пересобирать Next для prod с другими `NEXT_PUBLIC_*`; относительный same-origin API и runtime-конфигурация. Compile-time различия требуют отдельного ADR.
4. Выполнить применимые миграции одним исполнителем, readiness, smoke, E2E. Владелец принимает конкретный SHA. Если dev перешёл на новый SHA, принятие старого не переносится автоматически.
5. Только владелец вручную запускает production-релиз принятого SHA. Проверяются успешные checks/dev-приёмка/digests; prod-выпуски сериализуются. Агент не получает prod deploy-key и не запускает выпуск. GitHub Environments/reviewers зависят от тарифа, не предполагаются доступными; минимальный fallback из ТЗ — ручной trusted-owner workflow с ограниченным ключом и проверками SHA.
6. До рискованной миграции подтвердить свежий backup и проверенный restore-runbook. Migration-step одноразовый и неконкурентный; сбой останавливает выпуск, не допускает новую версию в трафик.
7. Развернуть те же digests. Новая версия попадает в трафик только после readiness. Smoke после переключения безопасен для реальных данных; тестовые анкеты не создаются среди настоящих. Записать SHA/digests/время/исполнителя/результат без секретов.

## Миграции и откат

Expand/contract: сначала совместимые поля/таблицы, затем перенос, удаление старого отдельным выпуском. Откат кода возвращает предыдущие совместимые digests; это не rollback БД. Автоматических разрушительных down-миграций нет. Если нужна реставрация backup, явно оценить потерю свежих данных и действовать по принятому runbook, не по совету «вернуть базу».

Liveness `/health` отвечает о процессе; readiness БД/медиа/других обязательных зависимостей добавляется отдельно и не должна ложно сигнализировать готовность. Условие истечения 90 дней проверяется HTTP/API независимо от cron: поздний worker не открывает сайт/RSVP и не удерживает слот (D-19–21). Soft-delete — не purge: дата окончательной очистки/восстановление Q-19 ещё открыты, их нельзя включить в автоматический релиз как принятые.

## Поздние операции и проверка их работоспособности

| Операция | Когда появляется | Как проверим |
| --- | --- | --- |
| PR checks | E1-02 после каркаса | Хороший PR проходит, намеренно сломанные typecheck/build блокируются |
| Test-БД/миграции | E1-05/06 | Чистая миграция, изоляция dev/test, отказ очистки dev/prod; конкурентный migrator не допускается |
| Закрытый dev | E1-03 после артефакта | Анонимный вход закрыт, синтетические данные, наружу не уходит тестовая почта |
| SMTP/Mailpit | Identity-задачи | Письма видны в перехватчике, reset одноразовый, нет внешней доставки из dev |
| Медиа/jobs | E2-03 | Сбой worker/S3, повтор задания, лимиты параллелизма, ready только после производных |
| Ручной prod workflow | E1-03b | Непринятый SHA отклонён, dev/prod digests равны, два выпуска не гоняются |
| Smoke/readiness/rollback | Dev-релиз | Сбой readiness не переключает трафик; возврат предыдущего совместимого комплекта обслуживает запросы |
| Backup/restore | До реальных данных | БД и медиа восстановлены в отдельную среду; измерены RPO ≤ 24 ч, RTO ≤ 4 ч; ротация/удалённые данные Q-10 |
| Мониторинг | До пилота | Контролируемый отказ/диск вызывают алерт, request_id связывает события, нет паролей/анкет в логах |
| Purge | После Q-19/10 | Удаляются только данные целевого проекта, повторы безопасны, другие проекты/каталог не затронуты |

Наличие workflow-файла/backup-файла не доказывает работоспособности выпуска/восстановления. Сейчас ни одна из этих операций не запускалась.
