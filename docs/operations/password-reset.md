# Восстановление пароля · backend E1-04c

Реализован backend по D-31; web-формы ещё нет. [Карточка](../product/e1-04c.md), [QA](../qa/e1-04c-report.md), [контракт](../architecture/authentication.md). Регистрацию с кодом эта задача не реализует: E1-04d/Q-21 отдельно.

## Запуск на Windows / PowerShell 5.1

Docker Desktop должен работать; Node 26.13.0/npm 11.20.0. Из корня:

```powershell
node scripts/local-db.mjs check
npm run db:migrate:dev
npm run dev:api:database
```

API — `http://127.0.0.1:3001`, Swagger для просмотра — `http://127.0.0.1:3001/api/docs`. Порт 15432 — PostgreSQL, не HTTP. Остановка helper — Ctrl+C. Для web-каркаса отдельный терминал `npm run dev:web`; формы восстановления там пока нет. Обычный `dev:api` не включает БД/почту автоматически.

Helper включает файловый перехватчик `.local-mail/` в корне. Письмо — JSON с UUID в имени; отправки в сеть нет. Каталог игнорируется Git, его нельзя публиковать или передавать в артефакт: там синтетические email и коды. По умолчанию HMAC-ключ эфемерен: перезапуск API делает прежние коды непригодными. Для согласованного ключа нескольких локальных процессов можно задать `RESET_CODE_SECRET` вне Git: минимум 32 случайных байта, чётное число hex-символов, без вывода в терминал. Это отдельный секрет, не CSRF_SECRET.

`LOCAL_MAIL_DIR` — необязательное переопределение абсолютного локального пути. Без этого значения reset закрыт 503; production запрещает файловый транспорт даже при явном значении. chmod 0600/0700 — дополнительные POSIX-права, не доказательство Windows ACL; использовать собственный закрытый профиль. Секрет и содержимое писем не печатать в диагностике.

## Проверка через PowerShell

Использовать только свой синтетический аккаунт из текущего register API (он пока работает без подтверждения D-30). Пример браузерного контекста:

```powershell
$base = 'http://127.0.0.1:3001'
$session = New-Object Microsoft.PowerShell.Commands.WebRequestSession
function Invoke-AuthPost($path, $payload) {
    $csrf = Invoke-RestMethod "$base/api/v1/auth/csrf" -WebSession $session
    Invoke-RestMethod "$base/api/v1/auth/$path" -Method Post -WebSession $session -ContentType 'application/json' -Headers @{ Origin = 'http://127.0.0.1:3000'; 'X-CSRF-Token' = $csrf.csrfToken } -Body ($payload | ConvertTo-Json -Compress)
}
```

1. Для собственного тестового email выполнить register с email/password или login существующего аккаунта. Убедиться, что GET `/api/v1/auth/session` с `$session` отвечает 200. Не создавать реальные аккаунты для smoke.
2. `Invoke-AuthPost 'password-reset/request' @{ email = $testEmail }` → 202, нейтральное сообщение. Проверить своё новое письмо в `.local-mail/` локально; не отправлять код в чат/лог.
3. `Invoke-AuthPost 'password-reset/confirm' @{ email = $testEmail; code = $code; newPassword = $newPassword }` → 204 без тела. `$code` — строка, ведущие нули сохраняются; пароль соответствует D-28.
4. GET session со старой cookie → 401. Старый пароль не подходит; login с новым → 200. Повтор confirm с тем же кодом → 400 RESET_CODE_INVALID. Новый аккаунт/Session при reset не выдаётся.
5. Повтор request — resend, не более трёх/email/час и десяти/IP/15 минут; 429 содержит Retry-After. Старый код после resend недействителен; срок нового — 10 минут; пять неверных попыток исчерпывают код.

Веб-браузер Swagger на порту API имеет другой Origin, поэтому Try it out не заменяет этот клиентский сценарий. Origin/CSRF намеренно не обходятся.

Команды проверки из корня: `npm run typecheck`, `npm run build`, `npm run api:openapi`, `npm test`; затем `npm run db:migrate:test` и `npm run test:database`. Последние работают только с проверенной отдельной test-БД. Никаких reset/schema push.

## Сбои и границы

- Запрос не раскрывает наличие аккаунта статусом/текстом. Недоступность локального транспорта до поиска email даёт общий 503. Ошибка доставки конкретного письма оставляет код неактивным и нейтральный 202: это принятие запроса, не гарантия доставки. Повторить request в пределах лимита. Старый код уже отменён; он не восстанавливается при сбое письма.
- Доставка вне транзакции; `deliveredAt` ставится только текущему UUID заявки. Запоздалое старое письмо не активирует старый код. При падении после записи письма до активации нужен новый request. Автоматического worker/retry доставки в этом PR нет.
- Неверный/истёкший/использованный код — одинаковая 400, пароль и сессии не меняются. Неверные попытки сохраняются транзакционно даже при ошибочном ответе. Ошибка внутри смены пароля откатывает пароль, код и отзыв сессий вместе.
- Счётчики PostgreSQL сохраняются между API-инстанциями; фиксированные окна, не sliding. Отклонённый запрос учитывается в IP-лимите, но не плодит email-ключи после его исчерпания. Trust proxy пока выключен: X-Forwarded-For не доверен. Production proxy требует отдельной настройки и проверки.
- Коды недействительны по времени без cron; автоматическая физическая очистка просроченных reset/limiter rows и старых локальных писем не реализована. Тесты удаляют только свои записи и свой временный inbox. Локальные письма очищать как синтетические данные, не использовать эту схему хранения для реальных пользователей.

До публичного запуска отдельно: реальный SMTP/провайдер, изоляция dev/prod, долговечный secret/rotation, надёжная очередь/повторы/метрики доставки, очистка метаданных, защита нагрузки и проверка временного канала перечисления email. Равенство статуса/текста не доказывает равенство времени, SMTP-доставку или production readiness. Регистрация D-30 также обязательна. Уведомление о завершённом сбросе рассмотреть вместе с production-почтой.
